# 1. 背景与问题

## 1.1 现状

历史记录包含扫码记录（`ScanRecord`）和生成记录（`GeneratedRecord`），按天分组、时间倒序展示。当前的入库行为是**每次扫码 / 每次生成都无条件新增一条记录**，仅有的去重手段是相机端 1.5 秒的会话内防抖（`ScannerView.dedupInterval`），只防连续误触，跨会话、跨天完全不去重。

现有入库路径盘点（以当前代码为准）：

| 入库路径 | 位置 | 现有去重 |
| --- | --- | --- |
| 相机实时扫码 | `ScannerView.swift` | 仅 1.5s 会话内防抖 |
| iOS 相册选图识别 | `ScannerView.swift` | 无 |
| macOS 批量图片识别 | `MacImageRecognitionView.swift` | 无（同批多码全部入库） |
| 二维码生成 | `GeneratorState` | 无 |

> 注：主 PRD v2.0 中「macOS 不记录扫码历史」的描述已过时，当前代码已将 macOS 图片识别结果持久化为扫码历史，本文以代码现状为准。

## 1.2 问题

- 同一个码（公司门禁、WiFi、收款码、常去的网站）每天扫一次，历史列表很快被相同内容灌满，一条内容出现几十条。
- 用生成器反复调试同一个内容（改颜色、改尺寸），生成历史出现大量「内容相同」的记录。
- 重复项把真正不同内容的记录淹没，用户找历史只能搜索或干脆「清空全部」，连带丢失有用记录。

## 1.3 用户价值

- 历史列表更清爽，单位屏幕内能看到的有效信息更多。
- 「这条码扫过几次」被保留下来，反而比重复堆叠更有信息量。

# 2. 目标与非目标

## 2.1 目标

1. **M1 — 手动合并（全程无弹窗）**：长按（iOS）/ 右键（macOS）任意一条记录，一键合并与它内容相同的整组记录；备注自动决策（点击记录的备注优先，否则取组内时间最新的备注），不需要用户选择。「···」菜单提供按类型分开的全局清理入口（扫码 / 生成各一项，各自确认）。
2. **合并不丢信息**：次数累加；备注按确定性规则保留，绝不静默清空已有备注。
3. **M2 — 自动去重开关**：设置页新增「历史记录自动去重」开关（默认开启）。开启后重复扫码/生成不再新增记录，改为次数 +1 并置顶、已有备注不重置；**开关从关拨到开时先弹确认框，确认后清理一次现有重复记录**并 Toast 汇报结果。

## 2.2 非目标

- 不做**相似内容**的模糊匹配（如忽略大小写、去掉 URL 的 utm 参数、忽略首尾空白）。一期只做精确匹配；模糊匹配作为后续增强另行评估。
- 不做跨设备 / 云端合并。
- 不做备注人工挑选界面——所有合并场景的备注均按确定性规则自动决策。
- 不改变现有的单条删除、批量删除、清空全部、保留时长清理等既有功能。

# 3. 术语定义

| 术语 | 定义 |
| --- | --- |
| 重复组 | 判定键完全一致的记录集合；组内记录数 ≥ 2 才算重复 |
| 保留记录 | 重复组中合并后留下的那条 |
| 冗余记录 | 重复组中合并后被删除的其余记录 |
| 备注集合 | 组内所有非空备注按**文字去重**后的集合 |
| 最新备注 | 备注集合中，所属记录 createdAt 最新的那一条备注 |
| 最近活动时间 | 扫码记录取 `lastScannedAt`、生成记录取 `lastGeneratedAt`，缺省回落 `createdAt` |

# 4. 方案总览

分两个里程碑交付：

| 里程碑 | 内容 | 价值 |
| --- | --- | --- |
| M1 手动合并 | 长按/右键逐组合并（无弹窗、点击记录优先）+ 全局清理按类型两项 + ×N 次数徽标 | 看到哪组乱就合并哪组；存量也可按类型一键清理 |
| M2 自动去重开关 | 设置开关（默认开）+ 开启时确认后存量去重 + 入库去重置顶 + 备注不重置 | 源头不再产生重复 |

主流扫码类应用的通行做法是「同一内容只保留一条、重复扫描时更新最近时间」。本项目历史页是按天分组的时间线形态，M1 手动合并不动排序语义；M2 的自动去重引入「重扫置顶」（排序与分组改用最近活动时间）。

# 5. 合并规则（核心）

## 5.1 重复判定键

| 记录类型 | 判定键 | 说明 |
| --- | --- | --- |
| 扫码记录 | `value` 完全一致（精确匹配，区分大小写） | `kind`、`source`（相机/图片）不参与判定：同一内容从不同来源扫入视为同一条 |
| 生成记录 | `content` + `configData` 完全一致 | 参数不同的同内容记录视为不同版本（不同样式的产物各有价值），一期不合并 |

> **注（生成记录 `configData` 精确匹配）**：`configData` 的判定依赖序列化结果字节完全一致。实现时必须保证相同参数的序列化具有确定性——推荐 `JSONEncoder` 启用 `.sortedKeys` 输出选项，或改为逐字段比较，避免因 Dictionary key 顺序不固定导致「相同参数被判断为不同版本」。技术方案（第 8 节）中有对应要求。

## 5.2 字段保留策略

重复组合并为一条保留记录，字段取值：

| 字段 | 合并后取值 | 理由 |
| --- | --- | --- |
| id / value（或 content） | **逐组合并**：取当前点击的记录；**全局清理 / 存量去重**：取组内最早一条 | 逐组以用户点击意图为准；全局无点击意图，取最早保持时间线稳定 |
| createdAt | 随保留记录（逐组 = 点击记录的时间；全局 = 组内最早时间） | 合并后记录停留在对应的那一天 |
| kind / source | 随保留记录 | — |
| note（备注） | 见下方备注规则 | 用户手写的备注不能因合并静默丢失 |
| scanCount（新字段） | 组内所有记录条数之和 | 保留「扫过几次」的信息 |
| generateCount（新字段，生成记录） | 组内所有记录条数之和 | 同上 |
| lastScannedAt / lastGeneratedAt | **保留保留记录自身的原值**，合并不刷新 | 手动合并没有「刚刚活动过」的事实，不伪造置顶 |
| thumbnailData（生成记录） | 取组内最新一条的非空缩略图 | 缩略图无信息差异，取最新即可 |

**备注规则（所有场景均为自动决策，无任何选择弹窗）**：

| 场景 | 规则 |
| --- | --- |
| 逐组合并：点击的记录有备注 | 直接用点击记录的备注（组内其他备注不参与） |
| 逐组合并：点击的记录无备注，组内无备注 | 置空 |
| 逐组合并：点击的记录无备注，备注集合只有一条 | 直接用该备注 |
| 逐组合并：点击的记录无备注，备注集合有多条不同 | **自动取时间最新的备注**，不弹选择框；createdAt 同秒并列时按稳定顺序（如 id）任取其一 |
| 全局清理 / 开关开启时的存量去重 | 组内取**时间最新的备注** |
| 自动入库去重（重扫 / 重新生成，M2） | 已有记录的备注**不重置**、不改动 |

## 5.3 合并示例

合并前（5 条相同内容，其中两条有不同备注）：

```
今天
  https://example.com/promo      相机 · 10-27 09:12   ← 备注「会员专属链接」
  https://example.com/promo      图片 · 10-27 08:30
昨天
  https://example.com/promo      相机 · 10-26 18:44   ← 备注「十月活动页」
三天前
  https://example.com/promo      相机 · 10-24 12:03
一周前
  https://example.com/promo      相机 · 10-20 09:40
```

长按「今天 10-27 09:12」那条 → 菜单显示「合并相同记录 (5)」→ 点击后**直接合并，无任何弹窗**。该记录有备注，备注优先用它；保留记录即点击的这条。合并后：

```
今天
  https://example.com/promo  [×5]   相机 · 10-27 09:12
                                    备注「会员专属链接」
```

若长按的是「三天前」那条（无备注）→ 合并后记录停留在「三天前」分组（时间取点击记录），备注自动取组内时间最新的备注，即昨天那条的「十月活动页」。

（M2 开启自动去重后，重扫该码会把这条记录提到「今天」分组并次数 +1，见 6.5。）

# 6. 功能需求

## 6.1 合并入口（M1）

### 主入口：长按 / 右键菜单（逐组合并）

- 位置：历史记录行的上下文菜单（iOS / iPadOS 长按，macOS 右键），排列为：`编辑备注` → `合并相同记录 (N)` → 分隔线 → `删除`。
- 文案：**「合并相同记录 (N)」**，N 为该重复组的总条数（含当前记录），点击前即可预期合并规模。
- **仅当该内容存在重复（组内 ≥ 2 条）时显示此项**；无重复的记录不显示，避免点击后无效果。
- 图标：`arrow.triangle.merge`。
- 扫码行与生成行均提供；生成行的 N 与合并范围按「内容 + 参数一致」计算。
- N 的计算基于**全量历史**（不受当前搜索词、码制筛选、来源筛选影响），与合并实际执行的范围一致；若此时有筛选激活，N 可能大于列表可见条数，这是正常现象。

### 辅助入口：全局清理（按类型分开）

- 「···」更多菜单提供**两项**（位于「清空全部」上方）：
  - **「合并重复扫码记录」**——只处理扫码记录的重复；
  - **「合并重复生成记录」**——只处理生成记录的重复（判定键为内容 + 参数）。
- **仅当对应类型存在重复时显示对应项**；两类都无重复时菜单中不出现合并项。
- 点击后弹各自的确认框，**计数只含当前类型**：标题 `发现 N 组重复扫码记录`（生成项为 `发现 N 组重复生成记录`），正文 `合并后将删除 M 条冗余记录，每组保留最早一条记录（留在其原有日期分组），并累计次数。此操作不可撤销。`，按钮 `合并`（destructive） / `取消`。
- 确认后执行 → Toast「已合并 N 组，清理 M 条记录」；点击时该类型已无重复（如菜单打开后数据变化的竞态）→ Toast「没有发现重复记录」。
- 全局合并的保留记录取组内最早一条、备注取组内时间最新的一条（见 5.2）；另一类型完全不受影响。

## 6.2 逐组合并流程（M1 核心）

1. 点击「合并相同记录 (N)」→ 按判定键（5.1）找出整组记录。
2. **直接执行合并，全程无弹窗**：
   - 保留记录 = 当前点击的记录（id、时间、码制、来源、lastScannedAt/lastGeneratedAt 原值全部随它）。
   - 备注按 5.2 备注规则自动决策：点击记录的备注优先；它没有备注时，组内备注唯一则直接用，多条不同则自动取时间最新的备注。
   - 次数累加为组内总条数。
3. Toast 反馈：`已合并 N 条记录`（N 为组内总条数）。

## 6.3 次数展示（M1）

- 历史列表行 trailing 增加**次数徽标**：`×N`（灰色胶囊样式，N ≥ 2 时才显示；N = 1 不显示，保持现有行外观）。
- 扫码详情页、生成回填页在时间信息附近增加一行：`共扫描 N 次` / `共生成 N 次`（N ≥ 2 时显示）。
- 生成记录列表行同样使用 ×N 徽标。

## 6.4 合并范围（M1）

- 逐组入口：只合并当前记录所在的重复组。组按全量历史计算，不受当前搜索词、码制筛选、来源筛选影响（组总是完整合并，不会只合并筛选可见的部分）。
- 全局入口：每个类型入口只处理**该类型的全部历史**，计数与执行均不涉及另一类型；同样不受筛选影响。
- 各入口共用同一套判定键（5.1）与字段保留策略（5.2）。

## 6.5 自动去重开关（M2）

### 设置项

- 设置页「历史记录」分组（现有「历史保留时长」所在分组）新增开关：**「历史记录自动去重」**，默认**开启**。
- 脚注说明：`同一内容只保留一条；重复扫码/生成时次数 +1 并移到最近时间，已有备注不变。升级后可前往「···」→「合并重复扫码记录 / 合并重复生成记录」清理已有重复数据。`

### 开关从关拨到开时（一次性触发，弹框确认）

1. 拨到开 → 计算现有重复（扫码按 `value`、生成按 `content + configData`，两类分别计算）。
2. **有重复** → 弹三按钮确认框：
   - 标题：`发现重复记录`
   - 正文：`开启前可先清理现有重复记录：扫码 N 组、生成 X 组，将删除 M 条冗余记录。此操作不可撤销。`（某类为 0 时该子句省略）
   - 按钮：`合并并开启`（destructive） / `仅开启` / `取消`
3. 点「**合并并开启**」→ 执行清理（保留记录取组内最早一条、备注取组内时间最新一条）→ 开关保持开启 → Toast「已自动合并 N 组重复记录（清理 M 条）」。
4. 点「**仅开启**」→ 开关保持开启，跳过存量清理；之后可用「···」→「合并重复扫码记录 / 合并重复生成记录」手动清理。
5. 点「**取消**」→ 开关**回滚为关**，存量数据不动。
6. **无重复** → 不弹框，直接 Toast「没有发现重复记录」。
7. 开关已处于开启状态时启动 App → 不重复触发。

### 开启期间的入库行为

- 相机扫码 / 相册识别命中已有记录（`value` 相同）→ **不新增**，更新该记录：`scanCount + 1`、`lastScannedAt = now`（自动置顶）；**已有备注不重置、不改动**。
  - 异常兜底：命中多条同 `value` 记录（如存量去重曾失败残留）→ 取 `createdAt` **最新**的一条更新，其余保持不变（可随后被手动合并）。
- 重新生成相同内容且相同参数 → 不新增，更新该生成记录：`generateCount + 1`、`lastGeneratedAt = now`（置顶）；备注不重置。
- 批量识别（iOS 相册多码、macOS 批量文件）同批次内出现相同 `value` → 批次内先去重，只保留一条；若该 `value` 同时命中已有记录，则按「重扫」逻辑处理（次数 += 同批重复出现次数，`lastScannedAt = now`，备注不动）。
- 扫码成功反馈（Haptic、Toast）保持现状，不因去重改变。

### 排序与分组

- 列表排序与日期分组改用**最近活动时间**（`lastScannedAt` / `lastGeneratedAt`，缺省回落 `createdAt`）：重扫旧码、重新生成后，该记录出现在「今天」分组顶部。

### 关闭开关

- 现有数据不做任何变动；新扫码 / 新生成恢复现状（每次新增一条）。

### 老用户升级首次启动

- 开关默认已处于开启状态，**不自动触发**存量去重（见待决策 #6），避免升级后静默重构用户数据。
- 为避免用户存量数据持续积累而不自知，通过以下两处引导用户主动清理：
  1. **版本 Release Notes** 中说明「新增历史记录自动去重，可前往历史页「···」菜单清理已有重复记录」；
  2. **Settings 页开关脚注**（见上方）已包含手动清理路径引导。

### 其他

- 扫码记录新增 `lastScannedAt` 字段后，详情页增加显示：`最近扫描 yyyy-MM-dd HH:mm`；生成详情同理。

# 7. 边界情况

| 场景 | 行为 |
| --- | --- |
| 逐组菜单项显示条件 | 仅当该内容存在重复（组内 ≥ 2 条）时显示；N 含当前记录 |
| 全局清理菜单项显示条件 | 仅当对应类型存在重复时显示对应项；两类都无重复时不出现合并项 |
| 点击记录有备注、组内其他记录也有不同备注 | 用点击记录的备注，其余备注随冗余记录删除 |
| 点击记录无备注、组内多条不同备注 | 自动取时间最新的备注，不弹选择框；createdAt 同秒并列时按稳定顺序（如 id）任取其一 |
| 组内多条备注文字相同 | 去重后视为一条 |
| 搜索 / 筛选激活时合并 | 逐组入口合并整组（组按全量历史计算，N 也按全量计算，可能大于当前可见条数，这是正常现象）；全局入口处理对应类型的全部历史 |
| iOS 编辑模式 | 任一入口执行合并均正常生效，完成后清空多选集合 |
| 合并执行中写盘失败 | 事务回滚，Toast 报错文案（沿用「历史记录写入失败：%@」），记录数不变 |
| 入库去重命中多条同值记录（异常残留） | 取 createdAt 最新的一条更新，其余不动 |
| 批量识别中某码同时命中已有记录 | 批次内先去重；再命中已有记录时按「重扫」逻辑（次数 += 同批出现次数，`lastScannedAt = now`，备注不动） |
| 开关从关拨到开，确认框点「合并并开启」 | 执行清理，开关开启 |
| 开关从关拨到开，确认框点「仅开启」 | 开关开启，跳过存量清理；可后续通过「···」全局清理手动处理 |
| 开关从关拨到开，确认框点「取消」 | 开关**回滚为关**，存量数据不动 |
| 开关已开启状态下启动 App | 不重复触发存量去重 |
| 开关关闭 | 现有数据不动；新记录恢复每次新增 |
| 与「保留时长清理」（applyRetention）并存 | 无冲突：清理只按 createdAt 删除；全局合并保留记录 createdAt 为组内最早，逐组合并后记录时间即用户点击的那条，均为正常时间线记录 |
| Spotlight 索引 / App Intents / Widget | 均不引用具体记录 id（Spotlight 只索引「扫一扫 / 生成二维码」入口），无连带影响 |
| 未来 iCloud 同步（v2.0 规划） | 合并 = 一批更新 + 删除的普通记录级操作，无特殊冲突语义；v2.0 设计同步冲突策略时复核即可 |

# 8. 技术方案概要（供研发参考）

- **数据模型**：
  - `ScanRecord` 新增 `scanCount: Int = 1`、`lastScannedAt: Date?`。
  - `GeneratedRecord` 新增 `generateCount: Int = 1`、`lastGeneratedAt: Date?`。
  - 均为「新增带默认值 / 可选属性」，走 SwiftData 轻量迁移，无需手工版本化 schema。
- **Settings**：`SettingsStore` 新增 `autoDedupEnabled: Bool`（UserDefaults 快照机制与现有属性一致，默认 `true`）。开关「false → true」跳变时由 SettingsView 发起存量清理流程（先算重复 → 弹确认框 → 调仓库执行 → Toast），仓库不直接依赖设置。
- **Repository**：`HistoryRepository` 协议新增：
  - `mergeScanGroup(of record: ScanRecord) throws -> Int`（返回删除的冗余条数）：以 `record.value` 找整组，保留记录即传入的 `record`（不刷新其 lastScannedAt），备注规则（点击记录优先 / 否则组内最新备注）在仓库内实现；
  - `mergeGeneratedGroup(of record: GeneratedRecord) throws -> Int`：同上，判定键为 `content + configData`；`configData` 的序列化必须具有确定性——`JSONEncoder` 使用 `.sortedKeys` 输出选项，或改为逐字段比较，确保相同参数的判定结果一致；
  - `mergeDuplicateScans() / mergeDuplicateGenerated() throws -> MergeOutcome`（`mergedGroups` + `removedRecords`）：两个全局清理入口与开关开启时的存量清理共用（后者两类各调一次），保留组内最早一条、备注取组内最新一条。
  - 备注决策规则具有确定性，全部收口在仓库层；视图层不直连 ModelContext。
- **入库去重（M2）**：扫码入库前按 `value` 查询命中记录（多条时取 createdAt 最新），命中走「更新」分支（次数 +1、lastScannedAt、备注不动），未命中走现有 `addScan`；或仓库提供统一入口（如 `recordScan(...) -> isNew`），实现时二选一。开关状态由调用方从 `SettingsStore` 传入，仓库不直接依赖设置。
- **视图**：
  - `HistoryView` 行的 contextMenu 增加「合并相同记录 (N)」（按组有重复才渲染，N 由内存中 @Query 数据计算）；「···」菜单按类型两项，同样由内存数据决定显隐。
  - 结果 Toast：当前 Toast 只在 `ScannerView` 内部实现，需在 `Shared/UI` 提供轻量 Toast 组件，历史页与设置页共用（设置页用于开关开启时的清理结果反馈）。
  - 无备注选择 Sheet——所有场景自动决策。
- **规范遵循**：文案走 `L10n.t(...)` 包裹；颜色字体用 `AppColor` / `AppFont` / `Spacing` / `Radius`，不硬编码；无强制解包、无 `as!`；UI 更新在主线程。

# 10. 验收标准

## 10.1 M1 — 手动合并

**逐组合并（主入口，全程无弹窗）**

- 组内 5 条同值记录，长按其中「今天」那条（有备注）→ 菜单显示「合并相同记录 (5)」→ 点击后**直接合并、无任何弹窗** → 剩 1 条 ×5，时间与备注即被点击那条的（记录停留在「今天」分组）。
- 长按组内一条**无备注**记录、组内备注唯一 → 合并后直接带上该备注。
- 长按组内一条**无备注**记录、组内有多条不同备注 → 合并后自动取**时间最新**的备注，无选择弹窗。
- 组内多条备注文字相同 → 视为一条，走「唯一备注」分支。
- 无重复内容的记录 → 长按/右键菜单中不出现合并项。
- Toast：`已合并 N 条记录`，N 为组内总条数。
- 生成记录：内容+参数一致的一组走同样流程（N 按此口径计数）；参数不同的同内容记录不属于该组，不受影响。
- 搜索/筛选激活时长按合并 → 组仍按全量历史完整合并。

**全局清理（按类型两项）**

- 「···」→「合并重复扫码记录」→ 确认框只统计扫码记录的组数与删除数 → 执行 → Toast「已合并 N 组，清理 M 条记录」；生成记录不受影响。
- 「合并重复生成记录」同理，只统计生成记录。
- 每组合并后：保留组内**最早**一条（时间停在最早的分组），备注取组内**时间最新**的一条。
- 某类型无重复时，对应菜单项不显示。
- iOS 编辑模式下执行 → 合并生效且多选集合被清空。

**通用**

- 合并后重启 App，结果持久化正确；旧版本数据迁移后 `scanCount` 默认为 1，原备注完好。
- iOS 模拟器与 macOS 两条 xcodebuild 验证命令均构建通过。

## 10.2 M2 — 自动去重开关

**开关跳变**

- 有重复时从关拨到开 → 弹确认框（按类型分行计数）→ 确认 → 执行清理 → Toast「已自动合并 N 组重复记录（清理 M 条）」。
- 确认框点「取消」→ 开关保持开启、现有数据未动，之后重复扫码仍按去重处理（次数 +1 置顶）。
- 无重复时拨到开 → 不弹框，Toast「没有发现重复记录」。
- 开关已处于开启状态时启动 App → 不重复触发存量去重。
- 关闭开关 → 现有数据不变；开关状态重启 App 后保持。

**入库行为（开关开启时）**

- 对同一码重复扫码 → 列表不新增行，原记录 ×N 次数 +1，移动到「今天」分组，**已有备注保持不变**。
- 重新生成相同内容且相同参数 → 不新增行，次数 +1 并置顶，备注不变；参数不同则正常新增。
- 异常残留多条同值记录时扫码 → 只更新 createdAt 最新的一条，其余不变。
- 批量识别 10 张图中含 3 张同一码 → 该码只入库 1 条，次数 +2。
- 关闭开关后重复扫码 → 行为与现状一致（每次新增一条）。
- 逐组合并一条带 `lastScannedAt` 的记录 → 该字段保留原值，不被刷新。

# 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 逐组合并无弹窗、直接生效不可逆，误触成本高 | 菜单项带条数 N 明示合并规模；备注自动决策规则确定性、不丢用户备注；撤销 Toast 列为首个增强候选（待决策 #2） |
| 开关开启时的存量清理会重构现有历史 | 三按钮确认框：「合并并开启」执行清理、「仅开启」跳过清理、「取消」回滚开关；用户意图清晰，无歧义 |
| M2 改变排序 / 分组语义，老用户发现「旧记录跑到今天」不适应 | 开关可关闭；脚注文案明确解释该行为 |
| SwiftData 轻量迁移在极端旧版本数据上出问题 | 上线前用旧版本 DB 文件做升级回归（重点：含备注的记录迁移后完好） |
| 大量重复时合并耗时（主线程） | 单事务批量操作；若实测超阈值（>0.5s）再考虑后台拆批 |
